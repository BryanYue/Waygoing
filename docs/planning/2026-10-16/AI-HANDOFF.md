## 3. Plan A 的需求：让现有工程流程能够被事件驱动

### 3.1 已确认的使用结果

用户希望在下班前留下一条需求、issue 或已可实施的 Jira 票，人在离开后系统仍能推进；下一次回来可以 review 已提交的 PR、测试证据和需要人判断的问题。这里的“离线做”指用户不在线参与，运行环境、必要网络和服务仍需工作。

期望流程为：

```text
Jira 分配／仓库 issue／聊天等需求入口
    ↓
识别项目、整理需求，创建或关联 Jira 票
    ↓
检查该票是否满足约定的实施条件
    ├─ 尚未满足 → 整理规格和问题 → 通知用户 review → 等待确认事件
    └─ 已满足 → 为该票启动或续接对应任务／会话及工作环境
                    ↓
              按现有规格实施 → 测试与证据 → 提交分支和 PR
                    ↓
              人工 review → 人工合并
                    ↓
              核对关联 PR 与完成条件 → 收尾并关闭对应 Jira 票
```

这描述业务方向，不是已经批准的数据库状态机或准确字段名称。

### 3.2 入口和 Jira 的职责

**已确认：** 入口不限于用户自己开的票，也包括 PM 分配给用户的 Jira 票、GitHub／Bitbucket 仓库里的 issue，以及未来 Slack 或其他聊天入口。聊天中讨论清楚的工作也可以整理成 Jira 票。具体先接哪个入口由 Plan A 提出取舍。

对这条工程工作流，**Jira 是最终驱动实施与记录实施资格的权威任务来源**。仓库 issue 或聊天消息进入后，可以先识别 bug／新功能，再创建或关联对应项目中的 Jira 票。不能把每个入口分别做成一套互不对齐的实施状态。

公司项目和对应仓库、工作目录、开发规格等会预先配置。运行时据此找到项目与环境；环境缺失时如何 clone、初始化、准备依赖或创建资源，仍需按真实项目确定。语音里“先建 Git、关联仓库”不能直接解释为每次都创建新的远端仓库。

### 3.3 实施资格与主动提醒

**已确认：** Jira 票已创建或已经分配给用户，并不自动表示规格已确认。

| 情况 | 期望行为 | 尚待细化 |
| --- | --- | --- |
| PM 新分配的票，尚无可实施标记 | agent 识别并通知用户有新票需要 review，可先整理规格与问题；待用户确认后继续 | 提醒渠道、消息内容、去重、等待期间可做的准备工作 |
| 新功能、较大流程或范围变更 | 先形成规格，经相关人工 review 后再进入实施 | 具体 review 人、要求、状态／标签以及规格版本 |
| 预授权范围内的简单 bug／小修改 | 可按用户事先授权的规则，开票后直接视为满足实施条件 | 哪些属于该范围、范围外和不确定时如何处理 |
| 用户 review 后改变状态或加标签 | 监听到变更后检查当前票的实际条件，再启动或续接执行 | 标签或状态名称、撤销／变化处理、重复事件处理 |

现有 Jira 流程可能没有 PM review 状态，用户提出可以先用标签标记“规格已 review、可以实施”。这是可选承载方式，字段名称和工作流配置尚未冻结。用户提到多人确认的例子，不据此固定所有大票都必须恰好三人审批。

**候选建议：** 人工通过与预授权规则通过分别保留来源，并关联对应的规格范围／版本；审批后需求发生实质变化时重新判定资格。普通自动化执行者不能用自行添加“人工 review 通过”标记替代用户确认。具体技术实现由计划提出。

### 3.4 实施、验证与收尾

**已确认：** 对已经可实施的票，系统应根据映射和现有流程完成任务理解、相应会话／环境准备、实现、测试、记录、分支提交和 PR。最终保留人工 review 与合并。

**候选建议／规划需回答：**

- 一个票对应的任务、会话、执行尝试、分支和 PR 如何关联；续跑时怎样避免另开重复任务。
- 一票多仓、多 PR 或部分合并时，何时允许关票；PR 已打开不能等同于票已完成。
- 测试结果怎样绑定代码版本、命令、环境及未运行项，如何把环境失败与行为失败分开。
- 用户 review 后的修改意见如何进入原任务；人工继续修改时怎样处理写入归属。
- 失败或信息不足时，向用户交付什么记录、能继续哪些工作，以及何时停止无信息增量的重试。

这些问题要形成可检查的计划，但不借本次整理改变用户既有正式验收。

### 3.5 起步范围与接口调查

**已确认：** 用户前期不想做庞大工程。优先考察现有 Codex、Claude Code、CLI、插件或轻量本地常驻服务，保留原生 runtime 执行已验证流程。已有 Codex 调 Claude CLI 的插件可复用，但不是强制依赖。

用户设想的“任务总管 agent”可解释收到的需求并协调任务；监听、持久化、去重和确定性状态推进是否需要模型，应单独判断。无需为了等待新事件，让一个模型会话永远不停生成或依靠无限压缩存续。

**待查证：** 常驻服务如何接收 webhook 或轮询，怎样程序化启动／续接原生任务，当前桌面会话是否接受相应消息，以及产品、账号和运行环境的限制。现有接口文档提供可研究路径，尚未完成本流程的端到端验证；“App 一直打开”本身不是接入成功的证据。参考入口见第 8 节。

**候选可靠性范围：** 重复／乱序通知、服务重启、休眠或断网、执行中规格变化、运行取消、进程异常、外部操作结果未知、权限与凭证失效、并行写入。这些要按最小闭环挑选必要场景，避免第一版直接变成通用大型调度平台。

### 3.6 Dot 应交付的 Plan A

计划应明确下列内容；调查不到的事实说明缺口，可独立推进的部分继续完成：

可供规划的验收情景包括：未 review 的新票触发提醒；人确认后启动；重复事件不重复开工；已授权简单修复可执行；失败留下有效证据；成功生成待人工审查的 PR；合并并满足条件后正确收尾。它们是计划应具体化的场景，不是本文新增的一整套已冻结测试。

## 4. Plan B 的需求：在亲自理解与设计中构建个人 Harness

### 4.1 产品与学习目标

**已确认：** 自建 harness 的目的包括深入学习 agent runtime、理解各家模型与适配方式，把现有流程逐步转化为提示词加程序化机制，形成适合自己部署和调整的系统，减少对单一产品完整封装的依赖。

长期定位是多用途个人 agent。Coding 是一项能力，未来还可能接入多家 API、语音、邮件／消息总结、资料处理、文档和表格、日常事务等。订饭等例子用于表达愿景，不是现在执行这些动作的请求。用户也考虑开源，让其他人可以获得较好的默认交付质量。

“75–85 分”表达稳定、实用的质量期望，没有对应已定义的量表、基准集或验收阈值。Plan B 可以提出如何逐步建立质量评估，不直接把这个说法变成数字承诺。

工程流程中的 Jira、Git、worktree 和 PR，应留在适合它们的工作场景；未来邮件、表格或生活事务不必都经过 Jira。长期愿景要影响扩展边界，但不要求第一版同时做完所有入口和能力。

### 4.2 技术方向与资源

语音中的“Deep Think”按上下文规范为 DeepSeek，此理解已经在对话中告知用户并得到后续承接。正式接入仍需确认实际服务与模型名称。订阅登录不等于自建系统的通用 API 凭证；不要从原生客户端提取凭证来替代已存在的正式 API 接入。

**已确认的授权更新：** 最初背景只允许讨论；用户在后续明确补充已有 DeepSeek／Gemini API，接受未来的真实 API 实验。不能再引用旧附件把“没有 API／永不允许调用”作为规划阻塞。本次交接没有发起模型实验，也没有在此确定无限调用额度。

**候选建议：** 先接一家跑通小机制，再接另一家做对照，便于分清公共机制与厂商差异。模拟响应、回放可以用于控制流学习；真实模型行为需用实际接口和明确条件验证。高效管理并发进程与让多个 agent 高质量协作是不同问题，Go 的选型不会自动解决后者。

### 4.3 最新确认的学习方式：用户先构思，AI 质询与辅助

这是本次讨论最重要的后段澄清，应保留为 Plan B 的设计约束。

**已确认：** 用户要承担关键思考、设计和实际动手过程，不要求每一行代码都亲手写。不能把一句需求交给 AI，让 AI 完整产出方案与实现，再把事后解释当作已完成学习。

每个学习单元按以下职责组织，具体粒度可以调整：

| 环节 | 用户的活动 | AI 的支持 | 应留下的可核对材料 |
| --- | --- | --- | --- |
| 建立概念 | 理解必要知识，明确本单元问题 | 解释概念、提供少量相关资料；给足起步支撑，不提前代做完整方案 | 概念范围、资料和待回答问题 |
| 首次设计 | 先整理自己的想法，以文字、图、伪代码或小段代码表达 | 帮助澄清表达，等待用户形成自己的推理 | 用户初版 plan／设计及假设 |
| 质询与修订 | 回答关键问题，修改自己的方案 | Codex 做针对性的设计 review，提出反例、遗漏和提示 | 问题、修订理由、尚未解决部分 |
| 实现与动手 | 亲手实现或修改当前学习机制的关键部分 | Claude 辅助实现、处理样板和重复代码、解释细节；可以承担大量代码工作 | 实际代码及用户动手的关键变化 |
| 运行与验证 | 先预测，再运行、读记录、解释差异 | 帮助构造可观察实验，定位模型／上下文／工具／权限／runtime 层次 | 预测、实际运行记录和解释 |
| 独立复核与补充教学 | 对照证据修正理解，尝试迁移 | Codex review 架构、代码、运行证据与理解，围绕新增发现补一段教学 | 真实问题、解释修正与下一步练习 |

用户称设计质询为“拷打”，含义是让自己的想法经得起追问与反例。它应聚焦当前机制，提供提示、反馈和收束条件，避免无止境扩题或让学习长期停留在审问阶段。用户提出以后可用专门 skill 承载这一方式；目前没有创建或安装该 skill。

关键机制的动手范围按学习单元选择，不能退化为只改一个无关常量来证明参与，也不能擅自规定所有核心代码都必须纯手写、AI 一律不得提供实现。资料、讨论和代码要对应同一实际版本，方便用户另开学习对话时接续。

### 4.4 Claude 与 Codex 的分工及依据

**当前起步分工：用户主导构思与方案；Claude 辅助实现和第一轮讲解；Codex 负责质询、架构／代码 review 与有增量的补充教学。**
