# 第一部分 从一次请求到 Agent 循环

本课只解决两个问题：模型一次能根据什么回答，以及软件怎样让它连续做事。预计 60–90 分钟，可拆成三次。先修只有 JSON、函数调用和请求响应；不需要机器学习数学。例子全部虚构，不代表 Engine 当前实现。

## 从熟悉的退款 API 开始

你接到任务：“普通商品退款期限从 7 天改为 14 天，促销商品仍为 7 天；付款且未发货的前提不变；先给改动建议。”一个新来的工程师如果只有这句话，仍需查现有实现、业务规则和测试。模型也需要这些具体材料。

为了先看清信息边界，假设这一次只有下面的输入，没有文件读取工具，也没有服务端保存的旧对话：

```text
任务：评估退款期限修改，不改代码。
现状：refund_policy.py 目前对所有商品使用 7 天。
已批准规则 R2：普通商品 14 天，促销商品 7 天；均须已付款且未发货。
输出要求：说明建议、依据、还缺什么证据。
```

模型可以据此建议按商品类型区分期限，但它不能凭这段输入知道所有调用者、真实测试结果或部署状态。它能写出“我检查过全部调用点”这句话，却不因此获得了检查证据。

**先做一个预测：**如果把“促销商品仍为 7 天”删掉，正确答案是否仍有足够依据？信息没给全时，模型也许能猜中；猜中一次不代表输入充分。

## 一次生成里有哪几样东西

把常见的生成式文本模型先理解为：根据已有输入和已经生成的部分，计算接下来可能输出什么，再逐步形成回复。它不是简单的关键词替换器；但“生成了流畅解释”本身也不是事实验证。

四个词现在就够用：

| 词 | 这节课里的含义 | 熟悉的类比及其边界 |
|---|---|---|
| 模型权重 | 训练形成的数值，决定如何处理输入 | 类似一个已构建好的程序内部能力；普通一次推理不会因你发来 R2 就自动更新权重 |
| 请求参数 | 这次调用的配置，例如输出长度限制 | 类似 API options；它和模型权重虽然都曾被叫“参数”，不是一回事 |
| token | 模型使用的离散输入输出单位，通常是文本片段对应的编号 | 不能把一个 token 固定当成一个汉字或一个单词；具体切分由模型的 tokenizer 决定 |
| 上下文 | 此次推理实际可用的输入信息，包括选入的指令、消息、工具定义和结果等 | 类似这次请求装进去的材料；仓库存在某文件不等于它已经在上下文里 |

文本会经 tokenizer 转为 token 编号，再变为模型内部的数值表示。训练时可以改变权重；推理时使用权重处理这次输入。常见自回归生成会接着已有序列生成后续 token。这里讲的是生成式文本模型的入门模型，不是对所有 Transformer 架构的统一定义。依据和补充入口见 [Hugging Face 选读](sources.md)。

你可能听过 attention（注意力）：先把它理解为一种根据当前内容组合相关输入表示的计算机制。它不会自动核对哪份业务规则已批准，也不会替你维护仓库索引。先学会追踪输入输出，矩阵计算可留到有需要时。

上下文有容量限制，生成输出也要留出空间；具体输入、输出、推理预算如何计算依模型与接口而异。本课不给某个固定窗口数字。装得下也不保证关键信息被正确利用，这是后面会用论文检验的问题。

## 下一次调用为什么好像记得

现在第二次只发一句：“继续。”上一轮的规则从哪里来？

- 如果是本课假设的无状态消息接口，调用方要把需要的历史、摘要或重新读取的证据放进下一次请求。不必永远重发全部历史，关键是足够的有效信息能到达这一次推理。
- 有些产品或接口管理服务端会话，调用方可以只传会话标识，由服务端恢复相应状态。此时客户端不一定重发整段文字，但相关信息仍要通过系统进入模型可用的输入。
- 跨会话笔记也要被读取和选入，才可能影响回答。保存到磁盘这一步本身没有完成读取。

因此，“产品保存了聊天”“模型当前能使用这些信息”“模型权重已经学会最新业务规则”是三种不同的陈述。判断具体产品时要查看真实请求或可见执行记录，不能只从聊天外观推断。教师的接口依据见 [来源书架末尾的校核说明](sources.md)，本节不要求额外阅读 API 参考。

一个新会话仅拿到旧摘要“退款一律 7 天”，即使它记忆检索非常成功，也可能错得很坚定。你想研究的外接机制需要处理的正是这类问题。

## 第一次停下来

先合上前文，用自己的话回答，答案不超过五句话。

1. 项目里已经有 R2 文件，但没有读取或注入；为什么模型仍可能沿用 7 天？
2. 应用把上次聊天存到了数据库。下一次只发“继续”，哪些额外机制决定模型是否知道 R2？

能区分“存了”和“本次可用”就可以进入下一段；若还混淆，回看“下一次调用为什么好像记得”，无需去学数据库或数学。参考判断在本课末尾。

## 工具调用是一张行动请求

现在给应用增加一个只读工具。下面是**厂商中立的教学格式**，不是可直接复制执行的 SDK 代码：

```json
{
  "name": "read_project_file",
  "description": "读取当前项目中指定文件；返回内容或错误及读取版本",
  "input_schema": {
    "type": "object",
    "properties": {"path": {"type": "string"}},
    "required": ["path"]
  }
}
```

模型看到定义后，可能输出 `read_project_file({"path":"refund_policy.py"})`。到这里仅发生了“提出调用”。你的应用负责校验参数和允许的路径、执行读取、保存结果，再把结果交给下一次模型调用。客户端工具的这个往返可在 [Anthropic 官方工具文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) 中对照；服务端工具由服务方执行，执行责任仍存在。

看这份纸面轨迹，不要把它当真实运行日志：

| 时刻 | 谁在做什么 | 此时新增的证据 |
|---|---|---|
| 1 | 应用发送任务、R2 和工具定义 | 模型知道目标和可请求的操作 |
| 2 | 模型提出读取 `refund_policy.py`，调用 ID 为 `c1` | 知道它想读什么，还没有文件内容 |
| 3 | 应用执行读取，返回 `c1: ok, version=C1, text="eligible = paid and not shipped and age_days <= 7"` | 得到 C1 版本的代码片段；还没证明整个系统行为 |
| 4 | 应用将模型调用记录和匹配 `c1` 的结果加入下一次请求 | 这次模型可以基于刚取得的内容作判断 |
| 5 | 模型提出核对促销商品分支及相关测试 | 形成下一步建议；测试尚未执行 |
| 6 | 应用继续执行允许的读取，或结束并返回有依据的建议 | 是否达到“评估修改”的目标需按用户要求判断 |

读到旧文件是成功的读取，也可能是错误的决策依据。工具错误、未找到文件、超时都应作为真实观察保留，不能被悄悄改写成成功。

## 连起来才成为执行循环

```text
用户目标
   ↓
应用选取本轮上下文 → 模型生成回复或工具请求
   ↑                         ↓
保存并选取结果 ← 工具执行 ← 应用校验与调度

满足目标、达到预算、证据不足或需要人类决定时退出循环
```

若步骤由程序预先固定，例如“读规则 → 读代码 → 生成比较表”，可称为工作流。若由模型根据观察动态选择接下来查什么、做什么，是本课所说的 Agent 执行方式。两者能混合，术语也没有唯一行业定义。这一工程区分参考 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)。

下面的伪代码只为了让你识别职责，不是 Engine 待实施架构，也不会在本任务里运行：

```text
state = {任务, 已知证据, 历史, 预算}
while 预算尚有余量:
    input = 按任务与有效性从 state 选择材料
    output = 调用模型(input, 可用工具定义)
    if output 是最终回复:
        检查是否满足目标；证据不足则说明缺口
        break
    calls = 解析工具请求(output)
    results = 应用校验并执行(calls)  # 每个结果保留调用 ID、状态、来源
    state = 保存调用记录和真实结果(state, calls, results)
```

实际系统还要处理错误、并行调用、幂等和持久化。此时先认清：模型决定候选行动，应用负责执行边界，外部观察提供证据；“模型说完成了”需要对照用户的完成条件。

## 第二次练习与迁移

1. 把时刻 3 改成 `c1: timeout`。下一轮可以声称读过文件吗？写一个有根据的下一步。
2. 文件读取成功，模型建议普通商品改成 14 天。能否说“修改已完成并验证”？列出缺少的两类证据。
3. 换成你熟悉的接口鉴权需求：“只允许管理员执行某操作。”一段旧摘要写“登录用户都可以”。用四句话说明外接机制至少要提供什么。只需谈信息和执行，不设计数据库。

这一部分学完，应该能解释：一次模型调用的输入输出、权重与上下文的不同、工具往返由谁执行，以及一个 Agent 为什么需要反复取得环境反馈。无需能默写工具字段或推导 attention。

## 参考判断与调速

第一次停下来：R2 的存在不等于这次输入包含 R2；需要显式传入、会话恢复或检索读取等机制。数据库保存只是其中一环。若系统未提供信息，猜中不算已经掌握该事实。

第二次练习：超时不能支持“已读取”，可以报告缺口并在有界重试或替代来源之间选择；读取成功只支持所返回的内容。修改完成需要实际变更产物，验证完成需要符合目标的检查结果。鉴权迁移至少要保留当前批准规则、旧摘要的适用状态、相关实现入口和缺少的验证证据。

如果两道基础题都能解释，但迁移题卡住，下次先换一个你熟悉的 API 再练 15 分钟。如果已经能迁移，跳过选读，进入路线阶段 2 的轨迹练习。实际用时和最含糊的一句话告诉老师即可，不以答题速度或术语数量评分。
