# 贯穿案例与练习

以下全部为本课程自编的纸面材料。文件名、版本标识和测试记录都属于虚构订单项目，不在 Engine 仓库中创建这些实现文件。无需运行命令。

## 按阶段解锁资料

阶段 1–2 只看 R1、R2、C1。阶段 3–5 再看 T1、N1、D1、I1。阶段 6 才揭开 R3。第一课可直接使用该课给出的短输入，不必先读完整表。

| 卡片 | 类型与来源 | 内容 | 观察与适用信息 |
|---|---|---|---|
| R1 | 已批准需求 `requirements/refunds-v1.md` | 已付款且未发货的订单，所有商品最多 7 天可退款 | 2026-09-01 记录，适用于 v1 |
| R2 | 已批准需求 `requirements/refunds-v2.md` | v2 普通商品改为 14 天；促销商品保持 7 天；付款及未发货前提不变 | 2026-10-01 批准，目标 v2；普通商品期限替代 R1，其他约束保留 |
| C1 | `refund_policy.py` 的旧版本片段 | `eligible = paid and not shipped and age_days <= 7` | 2026-10-02 从 C1 版本读取；这是现状，不是对 R2 已实现的证明 |
| T1 | `test_refund.py` 的旧用例记录 | 普通商品第 10 天预期 `False`；促销商品第 10 天也预期 `False` | 为 v1 编写；没有 v2 的新运行结果 |
| N1 | 旧交接摘要 | “退款一律 7 天，测试已通过。” | 摘自 v1 工作；没有测试版本/运行记录，不能扩展到 v2 |
| D1 | 已批准设计记录 `decisions/policy-location.md` | 退款期限由 policy 模块决定，HTTP handler 调用它；便于同一规则复用 | 2026-09-03；不规定必须为 7 天，也不证明所有调用点已找到 |
| I1 | 2026-10-03 的讨论建议 | “以后也许可以所有商品 30 天退款。” | 未批准；记录更晚不代表权限或适用性更高 |

## E1 一次调用

只给模型 C1，再问“如何支持普通商品 14 天退款”。它还缺哪些规则？添加 R2 后什么问题解决了，什么问题仍需查？用“模型已获得的证据”回答，不揣测模型内心是否理解。

## E2 工具轨迹

沿第一课的六步轨迹标注职责。将读文件结果依次设为：C1 成功返回、文件不存在、超时。每种情况写一句允许得出的结论。迁移到测试工具：如果仅有命令字符串，没有执行回执，可以报告什么？

## E3 给上下文挑材料

任务是评估 v2 的改动点，暂不修改代码。假设首轮材料空间只放四张卡片，这是教学约束，不对应某个模型的真实 token 数。选出四张并说出取舍；允许把其他卡片留下可继续读取的入口。

再把 R2 压成两句话，检查“普通/促销”“付款/发货”条件是否保留。为你的结论标注来源、观察时间、适用版本和是否被替代。比较“充分”与“简短”是否总能同时做到。

## E4 用不同方式检索

对三个查询分别挑一个起始方法，并写出它可能漏什么：

1. “谁调用 `refund_policy.py`？”
2. “为什么退款判断不放在 HTTP handler？”
3. “普通商品第 10 天是否可退？”

假设一次语义检索返回按分数排序的 N1、I1、R2。不要计算虚构准确率；指出为什么排序分数不足以直接选答案，以及需要追加哪种范围/状态检查。

## E5 交接记忆

写最多五条笔记交给新会话，内容至少包含当前目标、已知现状、决定依据、待核查项。每条保留来源入口；推测单独标明。再把笔记缩短一半，圈出因此损失的条件。

选择一个你自己的调试任务，把“试过什么/观察到什么/尚未排除什么”按同样形式写三句话。失败尝试可以保留，但不能把一次未成功操作写成“该方案永远不可行”。

## E6 需求变化后更新

现在揭开新卡片：

> R3：2026-10-04 批准，面向 v3；普通商品改为 21 天，促销商品仍 7 天，付款且未发货的前提保留。2026-10-05 系统才收到了这份记录。没有提供 v3 代码、测试和部署结果。

延续 E3 的 v2 评估任务；材料没有给出把本任务切换为交付 v3 的通知。交接时分别记录当前明确目标、已出现的新要求，以及是否切换目标这个待决定项。

1. 在不删除 R2 历史的情况下，更新自己的记忆卡。区分获知时间与目标规则的批准/适用信息；未给出生产上线时间，写“未知”。
2. 哪些直接事实和派生笔记需要检查？旧的 T1 能否因“新要求”被直接称为已通过新验收？
3. 写一个交接包，使下一位工程师能区分“对哪个版本应该如此”和“代码已经如此”，并知道是否切换目标尚未决定。

记录你手工查找用了几步、有没有漏项。若少量卡片下扁平笔记已很好用，保留这个结果，不需要把它写成失败。

## E7 关系图

只画四到八条有来源的关系，例如 R2 的普通商品期限被 R3 替代、C1 实现 R1 的旧规则、N1 来自旧任务、T1 覆盖旧预期。标记哪些是材料明示、哪些是你的推断。

沿关系找 R3 的候选影响范围。然后故意删除“摘要来自旧任务”这条边：系统还能发现 N1 可能过期吗？你会补原文搜索、定期检查还是人工确认？这里只演示漏边风险，不是图效果的实测。

## E8 一页比较设计

任选你熟悉的 coding 任务，用下面空表写草案。首次只设计，不运行；本任务没有恢复历史实验。

| 项目 | 你的填写 |
|---|---|
| 任务与指定时点 |  |
| 原始资料与正确判断依据 |  |
| 候选 A 按需搜索和简短交接 |  |
| 候选 B 检索和有来源笔记 |  |
| 候选 C 关系索引和增量更新 |  |
| 相同条件 | 模型版本、任务、原始信息可达性；另记录预算与工具差异 |
| 变化场景 | 无变化、规则改变、文件改名/删除、冲突未决、任务交接 |
| 观察 | 正确证据是否取到、旧规则是否当成当前规则、下一步是否正确、最终任务行为 |
| 成本 | 建索引、更新、回源检查、调用数、时延和上下文量分别记 |
| 对照 | 去掉时间过滤或关系链接后是否有差异；不要连数据和模型一起换 |
| 结论边界 | 小样本仅用于发现机制问题；扩大结论前需要多任务及重复观察 |

正确使用历史不计为“过期误用”。同一原始信息可达，并不强制所有方案每次输入完全相同；否则无法比较信息选择本身。端到端比较要算准备与更新成本，若只比查询时延，应明确口径。不要让评测答案提前进入某一候选的记忆。

迁移到非 coding 场景，例如客户支持政策变化，说明哪些仍通用（来源、范围、时间、交接），哪些需换掉（代码符号提取、测试入口）。图关系不必相同，评价任务也要重设。

## 尝试后再看的参考判断

- E1–E2：需获得商品类别、付款/发货等适用条件；读取错误保留为错误，提出命令不等于执行，执行成功也不等于覆盖全部需求。
- E3：R2、C1 通常不可缺。T1 支持识别需要调整的旧预期，D1 支持定位职责；其他合理取舍需解释任务目的与下一步入口。没有唯一卡片组合，不能把卡片名额当产品验收阈值。
- E4：符号/引用查询可从结构定位开始；设计理由回到 D1；第 10 天的问题已指定普通商品，还需确认目标 v1 或 v2 以及付款/发货前提，再按需求与当前实现分开作答。相似度不替你判批准状态。
- E5–E6：新规则不能自动改变已读取的 C1，也不能制造测试/上线证据。当前明确任务仍是 v2 评估，是否改为 v3 待决定；R2 对 v2 仍有效，对 v3 的普通商品期限则由 R3 替代。T1 的普通商品旧断言需按对应目标版本的已批准需求评估调整，但不能记录成已通过；促销商品例子仍有回归价值。
- E7：图的完整性和正确性是输入条件，不是“画了图”就有的保证。扁平表、搜索和图可以组合；别为说明图有用而故意隐藏扁平方案的信息。
- E8：先写可能失败的场景，再选择组件；论文的局部结果不能替你填“最终任务行为已验证”。
