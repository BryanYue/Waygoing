# 编排协议 v2.10 修订单（基于 v2.9）

Oct 15, 2026 · @RD-JIS-CTT-Bryan

## 使用说明

本单把 9 月 30 日审计的 16 条问题全部写成可直接放进协议的条文，按 v2.9 的章节定位套用；未提及的 v2.9 条文一律不动。

1. 引用块里的文字，以及紧随其后的表格，是写入协议的条文；其余文字是套用说明。
2. 每条标明动作：「新增」插入整段，「替换」取代所述的原规则，「追加」接在所述原句之后，「全文」为全文范围的统一替换。
3. 章节编号不变。新内容以 §0 之前的无编号节和各节末尾的新小节进入，现有 delta 与启动命令里对"§1 开工序列"等的引用继续有效。
4. 套用后标题改为 v2.10，修订记录按【7-B】追加。正在运行或待恢复的 v2.9 plan 继续使用 v2.9（【0-D】）。

下面三处按默认取值写入，需要你确认：

| 决定 | 本单的取值 | 备选 |
| --- | --- | --- |
| 收官两表由谁出（#1） | 独立只读审查席，不参与本阶段任何 lane；轻量模式由该 lane 的审查席兼任 | 协调者出表、审查席复核：便宜，但起草仍是自审 |
| 新测试转正路径（#3） | 红绿核验 + 审查席对照 delta 原句确认 → 候选 oracle → 阶段收官时 Boss 批量批准；delta 标注的范围改由独立席先写测试 | 所有 FEATURE 都由独立席出题：证据最强，成本最高 |
| 模式分几档（#11） | 两档：完整、轻量；轻量只收单 lane、MOVE 或 EDIT、不触判据面、无跨平台/下游/硬件闸的任务 | 三档，在中间加一档 |

与审计原建议不同的一处：测试比对按用例全名逐个比，不只比数量（【2-C】）。只比数量时，删一个旧用例、加一个新用例，数量不变就过了；跨模块搬迁还会误报。

## 新增：术语与角色

**【T】术语与角色** · 新增：置于 §0 之前，不编号

> 层级：plan ⊃ 阶段 ⊃ 波次 ⊃ lane。各角色能做什么、不能做什么，以下表为准。

| 角色 | 是谁 | 能做 | 不能做 |
| --- | --- | --- | --- |
| Boss | 人类负责人 | 批准 delta 与模式；授权变更（判据面、登记文件、已知红集合增项、lane 类型降级、删除用例）；裁决 DECISIONS；合并 PR | — |
| 协调者 | 主代理 | 拆 lane、写 dispatch、派工、跑闸、红灯裁决、写全部记录 | 批准或授权任何事；push 基线分支；merge PR；改写审查席的输出 |
| 执行席 | 被派去实现某个 lane 的代理 | 在本 lane 的 owned files 内写入 | 写 owned files 之外的文件；写判据面保护集与登记文件 |
| 审查席 | 只读代理，审 lane 或阶段产出 | 出 finding，初判 nature、blocks、scope；收官审查席出收官两表 | 写任何代码或记录文件，输出由协调者原样落盘 |

| 术语 | 定义 |
| --- | --- |
| plan | 一次完整改动计划：一份 delta、一份 dispatch、一个 state 目录、一条 task 分支 |
| 阶段 | plan 内由 delta 划分的里程碑；每个阶段结束过阶段收官闸 |
| 波次 | 阶段内同一轮派发的一组 lane，可以并行 |
| lane | 最小派发单元，带类型、owned files、模型、预算、闸命令与依赖 |
| lane 起点 | lane 开始时 task 分支的 HEAD；并行 lane 为其 worktree 的分叉点。所有 lane 级 diff 与检查都以它为基准 |
| 批准基线 commit | Boss 明确批准 delta 时登记的完整 40 位 commit，是冻结内容的唯一身份来源 |
| 登记文件 | 记录批准基线 commit、协议与 delta 的 sha256、判据面清单与哈希、approval\_source 和授权变更历史的文件，路径在 delta 中声明 |
| oracle | 已批准、已写入登记文件的验收判据：测试、期望值、golden 基准 |
| 候选 oracle | 已通过审查席确认、等待 Boss 批准转正的新测试（【2-I】） |
| 判据面 | oracle 以及一切能改变 oracle 判定结果的东西，分保护集与监视集（【6-A】） |
| 事实源文件 | 事实清单中某条事实的唯一定义文件 |
| 责任方 | DEBT 条目指定的处理者，为 Boss 或某个 lane |

**【T-全文】统一用词** · 全文

> "负责人" → "Boss"；事实清单语境中的 "owner 文件" → "事实源文件"；DEBT 语境中的 "owner" → "责任方"；"plan 分支" → "task 分支"；`<base>` → "lane 起点"。

## §0 修订：输入文件与模式

delta 新增四项冻结内容，已知红名单改为只减不增，并补上协议副本的权威规则和两档模式。

**【0-A】delta 新增四项** · 追加到 delta 必含内容清单

> delta 另须包含：
>
> 1. 必需覆盖清单：按闸分列（MOVE、EDIT、FEATURE 波次闸，阶段收官闸），列出必须实际执行的检查项，逐项可机检，如测试任务全名、平台目标、静态检查任务、下游检查。
> 2. 判据面清单：保护集与监视集的具体路径或 glob，以及禁用的 record/update 类任务与参数（【6-A】）。
> 3. 模式：完整或轻量（【0-E】）。
> 4. 独立出题范围（可选）：需由独立席先写测试的 FEATURE 范围，每项附验收场景：delta 原句出处、前置条件、操作、期望结果。

**【0-B】覆盖不减的判定** · 追加到"dispatch 不得减少 delta 要求的覆盖"之后

> 是否减少覆盖，以闸的必需覆盖核对（【2-B】）结果为准，不以协调者的说明为准。\[M\]

**【0-C】已知红名单** · 替换原规则

> delta 中的已知红名单是上限，只减不增。运行时的"当前已知红集合"记在 PROGRESS，初值等于 delta 名单。
>
> 1. 集合中的测试在任一闸中通过，即移出集合并记 PROGRESS；之后再红，按新红处理。\[M\]
> 2. 向集合新增测试须经 Boss 授权。\[M\]
> 3. 每项仍须有带期限的 DEBT；到期仍红 → 升级进 DECISIONS，不自动延期。\[M\]

**【0-D】协议副本的权威性** · 替换"唯一权威副本"的相关表述

> 新 plan 开工时以全局权威副本为准：复制入仓，sha256 写入登记文件。运行中或恢复的 plan 以其批准基线 commit 中的仓库副本为准，不随全局副本升级。开工或恢复时，delta 首行声明的协议版本与 sha256 必须与所用副本一致，不一致 → 停，写 DECISIONS。\[M\]

**【0-E】模式与准入** · 新增：§0 末尾新小节

> 模式由 Boss 在批准 delta 时确定。升档（轻量 → 完整）协调者可直接执行并记 PROGRESS；降档须 Boss 授权。执行中不再满足轻量准入（如需要改判据面或拆成多个 lane）→ 立即升档。\[M\]

| 模式 | 准入（全部满足） | 可免 | 不可免 |
| --- | --- | --- | --- |
| 完整 | 默认 | — | — |
| 轻量 | 单个 lane；类型为 MOVE 或 EDIT；不触及判据面；无需跨平台、下游、硬件闸 | 阶段划分（整个 plan 算一个阶段）；独立收官审查席（由该 lane 的审查席兼出收官两表，MOVE 无审查席时以【2-E】的判定输出代替对账表）；事实清单为空时免单源性审计 | 判据保护四层；所有闸通用检查【2-A】至【2-D】；红灯上限【3-D】；合并权留给 Boss |

> 原 §6④ 中的"较轻模式"改为指本节的轻量模式。

## §1 修订：开工

开工时就留下可复核的基准和登记保护，之后所有比对都以此为起点。

**【1-A】基线闸留证** · 追加到"先跑一遍基线闸"之后

> 基线闸按【2-A】生成执行凭证，并记录用例级结果，作为【2-C】比对的首个基准。\[M\]

**【1-B】登记文件就位** · 新增

> 开工前确认三点：登记文件位于 delta 声明的路径；它已在执行席与审查席的沙箱 denyWrite 中，也在 Write/Edit hook 的拒绝清单中；其中记录的协议与 delta sha256 与仓库文件一致。任一不满足 → 停，写 DECISIONS。登记文件的每次变更都是单独的 commit，说明中引用 approval\_source（【6-C】）。\[M\]

**【1-C】被忽略文件的哈希** · 新增

> 判据面中被 gitignore 的文件，登记时（最迟开工时）逐个计算 sha256 写入登记文件，供【6-B】比对。\[M\]

## §2 修订：闸

所有闸新增四项通用 \[M\] 检查；MOVE 改为归一化判定；EDIT 的"行为不变"改由审查席判断；FEATURE 新增红绿核验与新测试转正。

**【2-A】执行凭证** · 新增：所有闸通用；同时替换 EDIT 中按时间戳校验测试结果的规则

> 每次闸运行生成执行凭证，记录：HEAD sha 与 `HEAD^{tree}`；运行前后的 `git status --porcelain` 输出；闸命令原文；各结果文件的路径与 sha256；各任务是否缓存命中。凭证有效的条件：HEAD 与 tree 等于当前值，且运行前后工作区都干净。时间戳不再作为任何证据。\[M\]

**【2-B】必需覆盖核对** · 新增：所有闸通用

> delta 必需覆盖清单中对应本闸的每一项，在凭证中都要有结果：测试类执行数大于 0，其他检查类须实际执行；缺一项即 FAIL。缓存命中视同执行，凭证须注明。\[M\]

**【2-C】用例比对** · 新增：所有闸通用

> 以测试用例全名（任务或平台目标 + 类名 + 方法名）为单位与基准比对。lane 级闸的基准，是凭证 HEAD 等于 lane 起点的那次通过的闸；阶段收官闸的基准，是 task 分支上最近一次通过的闸；首个基准是开工基线闸。
>
> 1. 本次运行的每个测试任务中，基准里执行过的用例必须仍被执行，不得消失或变为跳过；`@Ignore`、`@Disabled`、assumption 失败都算跳过。
> 2. 改名或跨模块搬迁的用例，按 PROGRESS 中的全限定名替换表映射；搬迁时闸须同时运行原任务和新任务。
> 3. 失败只允许出现在当前已知红集合内（【0-C】）。
> 4. 新增用例不受限制；凭证另记各任务的执行数、跳过数、失败数。
>
> 任一不满足即 FAIL；确需删除用例须经 Boss 授权。\[M\]

**【2-D】owned files 越界检查** · 新增：所有闸通用

> 闸前 lane 的改动必须已全部提交。`git diff --no-renames --name-only <lane 起点>..HEAD` 列出的每个路径都必须匹配该 lane 的 owned files；`--no-renames` 让重命名的新旧两个路径都参与检查。越界即 FAIL。\[M\]

**【2-E】MOVE 判定** · 替换"`git diff --name-status -M100%` 每行须为 R100"的规则

> MOVE 以归一化后内容是否相同来判定，不依赖 git 的相似度阈值，diff 范围为 lane 起点到 HEAD：
>
> 1. 每个删除路径都须与一个新增路径配对，二者归一化后内容完全相同；
> 2. 每个修改路径归一化后与 lane 起点版本相同；
> 3. 归一化只剔除四类机械改动：`package` 声明行；`import` 行的增、删、改与重排；只含空白的行；全限定名替换表中的一一替换（旧名 → 新名，替换表写入 PROGRESS，适用于代码、资源与配置文本）；
> 4. 二进制文件要求逐字节相同。
>
> 任一不满足 → 该 lane 不是 MOVE，改按 EDIT 过闸。\[M\]

**【2-F】EDIT 的"行为不变"** · 替换原 \[M\] 标注

> "行为不变"由该 lane 的审查席判断，结论与依据写入 findings.jsonl（phase=gate-R）。审查席认定行为已变 → 该 lane 按 FEATURE 重新过闸。\[R\]

**【2-G】lane 类型只升不降** · 新增

> lane 类型只能按 MOVE → EDIT → FEATURE 的方向调整；降级须经 Boss 授权。所有类型变更列入 final.md 的"协调者变更"一节（【5-C】）。\[M\]

**【2-H】FEATURE 红绿核验** · 新增：追加到 FEATURE 闸

> 本 lane 新增的测试，在 lane 起点的代码上运行必须不通过（失败或无法编译），在 lane HEAD 上必须通过。在起点就通过的新测试不算新行为的证据，除非审查席写明它验证的是什么。\[M\]（运行）\[R\]（例外）

**【2-I】新测试转正** · 新增

> 1. FEATURE lane 通过波次闸，含【2-H】。
> 2. 审查席（非本 lane 执行席）逐条核对：每条与新行为相关的 delta 原句，至少有一个测试断言它，且断言的是需求要求的行为，不是实现细节。输出转正清单：测试 ↔ delta 原句 ↔ 断言摘要。\[R\]
> 3. 清单内的测试成为候选 oracle，sha256 记入 PROGRESS；之后对它们的任何修改都须重走第 2 步。\[M\]
> 4. 阶段收官时，转正清单随 final.md 交 Boss；批准后按授权变更写入登记文件，从此受四层保护。\[M\]
>
> Boss 批准前，候选 oracle 可作收官对账的证据，但须标"候选"；未进清单的新测试不作验收依据。

**【2-J】独立出题** · 新增：适用于 delta 标注的独立出题范围

> 由独立席依据 delta 中的验收场景先写测试，该席不执行、也不审查对应的实现 lane。这些测试在实现 lane 开始前提交，不在实现 lane 的 owned files 内，实现 lane 对其只读（由【2-D】保证）。实现完成后同样走【2-H】与【2-I】。\[M\]

**【2-K】oracle 完整性检查扩展** · 替换原 FEATURE 的 oracle 完整性检查范围

> oracle 完整性检查适用于 EDIT 与 FEATURE，EDIT 由其审查席兼做；MOVE 由【2-E】保证。默认算 Blocker 的情形，在放宽断言、删断言、新增 `@Ignore` 之外追加：新增 `assume*` 或其他条件跳过；改动测试 fixture 或测试数据使断言变弱；改动判据面监视集中的测试相关配置。\[R\]
>
> 闸命令不得包含判据面清单中禁用的 record/update 类任务与参数。\[M\]

## §3 修订：review 与红灯裁决

finding 分类权交给审查席，协调者降级必须留痕；suppress 与 tamper 自动成为 finding；红灯裁决加上另派上限，每个 lane 的尝试次数从此有界。

**【3-A】分类权** · 替换"由协调者给 finding 分类"的相关表述

> nature、blocks、scope 由审查席初判。协调者可以改判，但降级（CODE → REG，阻断 → 不阻断）须在 findings.jsonl 的 `downgrade` 字段写明原值与理由，并列入 final.md 的"协调者变更"一节。未分类仍按阻断处理。\[M\]（留痕）\[R\]（分类）

**【3-B】suppress 类标注** · 新增

> 生产代码 diff 中每新增一处 suppress 类标注（如 `@Suppress`、`@SuppressLint`、`@SuppressWarnings`、`//noinspection`、detekt 或 ktlint 的禁用注释），自动生成一条 finding：nature=CODE，blocks 默认阻断。审查席确认合理后可改判为不阻断，须写明理由。\[M\]（生成）\[R\]（改判）

**【3-C】oracle-tamper 记账** · 新增，恢复 v2.3 的记账

> 沙箱或 hook 每拒绝一次对判据面或登记文件的写入，都记一条 finding：phase=oracle-tamper，含执行席、路径、工具（Write、Edit 或 Bash）与拒绝来源。出现该类 finding 的 lane，在其审查席查看尝试的上下文（为什么要改判据）并给出结论之前，按阻断处理。\[M\]（记录）\[R\]（结论）

**【3-D】红灯裁决** · 替换原"自修一轮后三选一"的规则

> 1. 闸红后，执行席自修一轮。
> 2. 仍红 → 协调者三选一：另派、回退本 lane、park 交 Boss。
> 3. 每个 lane 最多另派一次，PROGRESS 须写明换了什么（执行席、模型或拆分方式）。另派的执行席默认从 lane 起点重新开始，同样只有一轮自修。
> 4. 另派后仍红 → 只能回退或 park。
>
> 单个 lane 的尝试上限因此固定为四次：首次执行、一轮自修、一次另派、另派后一轮自修。\[M\]

每次闸红往下走一格，任一格过闸就合入；走到底只剩回退或 park。

## §4 修订：并行与合并

并行 lane 改为 rebase 后重跑闸再 fast-forward 合入，回退改为按 lane 的提交整体回退，越界改动不再被保留。

**【4-A】并行前提** · 新增

> 同一波次并行 lane 的 owned files 两两不相交，派发时校验；相交的 lane 不得并行。\[M\]

**【4-B】合入流程** · 替换"合并优先 fast-forward"

> 1. 同一波次中第一个通过波次闸的 lane，fast-forward 合入 task 分支。
> 2. 其后每个 lane 先 rebase 到 task 分支最新 HEAD，以 rebase 的目标 commit 为新的 lane 起点重跑本 lane 的波次闸，通过后 fast-forward 合入；重跑变红 → 按【3-D】处理。
> 3. rebase 冲突说明 owned files 实际有交叉，属派发错误：该 lane 回退或 park，协调者修正 dispatch 后重派，不在冲突上手工合并。
> 4. cherry-pick 只用于以上流程走不通的例外，PROGRESS 须写明理由。
>
> &#91;M\]

**【4-C】回退** · 替换"未过闸的 lane 只回退其 owned files 中的改动"

> 未过闸的 lane 回退自 lane 起点以来的全部提交与工作区改动：串行 lane 让 task 分支回到 lane 起点；并行 lane 丢弃其 worktree 分支。回退不触碰其他 lane 的提交，越界改动随本 lane 一并回退。\[M\]

## §5 修订：落盘

DECISIONS 的默认动作只剩两种安全选项，收官两表改由独立审查席出，final.md 新增"协调者变更"一节，让 Boss 在 PR 阶段一眼看到协调者改过什么。

**【5-A】DECISIONS 默认动作** · 替换原规则

> 每条 DECISIONS 的"无回复时默认动作"只能取以下两种之一：
>
> 1. 相关 lane 保持 park，继续执行不依赖此决定的工作；
> 2. 停止整个 plan。
>
> 默认动作不得改变 delta、判据面、登记文件、当前已知红集合或任何合并状态；Boss 未回复不构成授权。\[M\]

**【5-B】收官两表** · 替换"阶段收官时必须出两张表"的出表人

> 对账表与单源性审计由收官审查席出。该席只读，不参与本阶段任何 lane 的执行或审查，模型档位不低于协调者。协调者原样存档其输出（附席位、模型、时间），final.md 引用原文；协调者有不同意见时另写一段并进 DECISIONS，不得改写表格。轻量模式见【0-E】。\[R\]（出表）\[M\]（原样存档）

**【5-C】final.md 的"协调者变更"一节** · 新增，为空也写"无"

> 逐条列出协调者在本 plan 中做的以下改动，每条写原值、新值、理由，以及 PROGRESS 中对应记录的位置：
>
> - dispatch 中闸命令、lane 类型、审查席数与预算的修改；
> - finding 的降级改判（【3-A】）；
> - 收官项"按适用选择"时未选的项。
>
> &#91;M\]

**【5-D】记录项补充** · 追加到 §5 的记录表

> PROGRESS 另记：当前已知红集合（【0-C】）；候选 oracle 及其 sha256（【2-I】）；全限定名替换表（【2-E】）；标 `uncalibrated` 的阈值（【6-D】）。findings.jsonl 新增 phase `oracle-tamper`（【3-C】）与字段 `downgrade`（【3-A】）。\[M\]

## §6 修订：元规则与判据保护

判据面扩成"保护集 + 监视集"，四层保护的第③④层随之更新，并补上冷启动取值和 \[M\]/\[R\] 标注规则。

**【6-A】判据面** · 新增：置于四层保护之前

> 判据面 = oracle 以及一切能改变 oracle 判定结果的东西，分两个集合；具体路径与 glob 写在 delta 的判据面清单中。

| 集合 | 内容 | 执行中能否写入 | 检查 |
| --- | --- | --- | --- |
| 保护集 | oracle 文件；golden 与 snapshot 基准；lint、detekt 等 baseline 文件；覆盖率与静态检查阈值的独立配置文件；登记文件 | 不能，由第①②层拦截 | 第③层 diff 与哈希比对 \[M\] |
| 监视集 | 与业务改动同在一个文件、影响测试判定的部分：构建脚本里的 test filter、include/exclude、testOptions 与测试任务依赖；测试运行器配置；CI 中的测试步骤 | 能 | lane diff 触及即自动记 finding，nature=CODE \[M\]；审查席判断是否改变测试选择范围或阈值，改变则阻断，须 Boss 授权 \[R\] |

**【6-B】第③层（验收）** · 追加

> 判据面中被 gitignore 的文件不在 `git diff` 与 `git status` 的视野内，改为逐个重算 sha256，与登记文件比对（【1-C】），不一致即阻止验收。\[M\]

**【6-C】第④层（授权变更）** · 替换

> 只有 Boss 能发起授权变更。每次变更的 approval\_source 必须是 Boss 的原话（消息原文或批准记录的引用），不能由推断、默认动作或"未表示反对"构成。变更以单独 commit 写入登记文件；验收时核对自批准基线以来登记文件的每个变更 commit 都带 approval\_source，缺一即 FAIL。\[M\]

**【6-D】冷启动** · 追加到"阈值只写进 dispatch"之后

> 本仓没有同类 lane 的实测时，取保守初值，即更早触发停止或升级的一侧：预算偏紧、并行度偏低、审查席偏多。该值在 dispatch 中标 `uncalibrated` 并记 PROGRESS；首个同类 lane 实测后按实测重算，记录前后值并去掉标记。\[M\]

**【6-E】标注规则** · 替换开头关于 \[M\] 与 \[R\] 的说明

> &#91;M\]：由命令或脚本给出确定结果的检查，条文须写出检查对象与通过条件。\[R\]：需要判断的规则，条文须写明由哪个角色判断、结论落在哪个记录（文件与字段）。一条规则同时含两类成分时分开标注。
