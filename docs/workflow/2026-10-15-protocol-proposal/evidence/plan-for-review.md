# 通用工作与编排规格修正方案
来源：coordinator 提案；供独立审查，不是用户已批准的新规则。
目标：以 W01–W12 和 Orchestration Protocol v2.9 为基础，在现有改善计划与修订单复核结论上形成工具中立的 v2.10 候选规格。交付候选，不直接安装到全局文件。

## 用户已经明确的方向
- 核心是两份现行规格。可以只用 Codex，也可以只用 Claude；跨产品插件是可选适配，不是协议必经层。
- 复杂任务启用协调者后，协调者不实施代码、不编写验收测试、不做代码审查；专业席处理。
- 实现与验收测试作者分开；独立审查检查两者和运行证据。lane 只用于需要拆分、协调、分阶段验收的较大任务，不包装所有小改动。
- 实际 worktree 在首次写入前登记。新测试需要记录测试目标和失败原因。
- 任务状态可持续，执行会话可以换新，不能靠一个会话无限压缩维持长任务。
- 未来希望发展自己的 harness，并覆盖 coding 以外事务；本轮先形成通用规格。
原话以 user-messages.json 和本次 plugin packet 为准。旧文章和审计意见是待核验材料；旧消息中“Codex 确认”已被后续工具中立要求纠正。

## 拟采用的整体设计
1. 规格定位与层次：v2.10 是现有 Orchestration Protocol 的候选替代正文，不建立第三份永久权威。通用原则可复用 W06–W11，客户端型号路由保留在客户端适配。采用前现行文件与已运行计划不变；新任务采用发布版，旧任务固定其已确认版本。
2. 适用范围：简单任务直接处理，不强制 lane、计划目录、worktree、独立收官席。需要新增验收测试可短时委派独立测试作者，仍不必建 lane。需要多方写入、依赖协调、长时恢复或分阶段验收时启用编排。是否启用由任务结构和风险决定，不按仓库大小、文件数或 FEATURE 标签自动决定。
3. 角色：人类负责人决定尚未授权的正式目标/验收/职责/外部操作；协调者拆分、派发、登记、调度、核对证据完整性及执行有效裁决；实施席写实现；测试席从正式要求构造测试；审查/确认席不参与相应候选的实现和测试，可兼任收官确认。协调者可以提出异议，但不能自行降级技术 finding。必要技术争议由独立审查职责裁定，改变用户要求仍按 W10。
4. 独立性：以实际实例、角色、写入范围及候选身份判断，不以跨厂商或模型强弱替代。审查输入包含原始要求、完整相关产物、版本和原始证据；无需继承作者完整推理。只读意味着不改候选，可在隔离环境执行必要验证。小任务的主代理可为实施者，不自动视为协调者。
5. 计划与写入：每个编排任务有稳定 task_id；候选有版本；运行会话有独立 run/session id。开工明确目标、非目标、基线、输入、约束、验收、写面、停止与回滚条件。每个资源同一时段一个写入者；实现和测试有分离写面，交接前停止原写入者。按需使用阶段/波次/lane，不强制空层级。
6. 工作区登记：记录真实路径、来源基线、当前候选、负责实例、owned resources、保护配置和在途任务。新工作区在首次使用前补登记，不要求预建所有未来 worktree；登记是授权内执行，不自动要求再批准。既有脏内容不能清理、stash 或漏掉；依赖未提交输入时明确打包/标识。
7. 验收与保护：正式要求、契约、基线和验收不因换模型、压缩或变更记录失去效力。保护集锁定正式判据；监视集跟踪验收选择、阈值和证据生成配置，触及不自动等于缺陷。保护描述必须说明实际宿主可执行能力与覆盖；事后 diff 不冒充事前权限。授权更新只纳入获准差异，同步登记、权限与验收引用；缺少必需保护只停相关工作，不能自降标准。
8. 测试：测试作者独立，实施者可提异议但不能单方面修改断言。测试可用作证据、独立确认、纳入保护登记和用户改变正式验收是不同状态。既有回归基线、新测试预期失败、候选最终结果分别留证，允许合法 TDD 起点为红。编译失败/环境故障/测试假设错误不等于目标行为失败；新 API 不存在时注明证据边界。测试名称/数量变化是检测信号，是否保持必需覆盖由证据判断。
9. 执行凭证：记录候选实际输入身份、命令或操作、环境/配置、结果、产物版本、必要日志、执行者、缓存/历史证据来源。仅 HEAD/tree/status 干净不足以证明全部输入；重要保护内容应核实真实字节/资源版本，处理隐藏索引标志、忽略输入、路径别名及外部资源。未运行、未知、环境阻塞不得记通过。缓存可复用须满足输入和适用性条件，不能冒充新的真机/外部验证。
10. finding：有稳定 id、证据、目标/版本、性质、阻断性、范围、责任与关闭依据；修复、误报、重复、过期等分别记录。记录为债务不等于验收通过。协调者路由，不自行改判；拒写尝试保留观察和原因，不一律推断恶意。
11. 修复与集成：失败先分类；无新信息停止重复尝试，必要时另派，复用有效成果。换实例/拆 lane 不清零同一问题的尝试与成本。Git 集成依项目选 merge/rebase，不以冲突证明写面必重叠。保留不可变原始起点与可变集成起点；实质变更使受影响证据失效；语义冲突由相应作者处理。回退前核实归属和可恢复性，不默认重置共享 task 分支。
12. 会话生命周期：任务状态持续，会话按边界换新。阶段开始定义有限目标与检查点；阶段结束评估换新，审查使用独立上下文。约束丢失、反复无信息增量、无法可靠恢复时先校正，仍不可靠则交接。无统一固定 token 比例/压缩次数。停止新派发→检查点→确认旧写入者停止或明确继续归属→新实例按原始依据和实况恢复→记录责任接手→实际结束旧运行。继承历史的 fork/resume/compaction 不冒充 fresh。迟到结果不得直接覆盖当前候选；工具不支持停止/关闭时记录实际限制，不用聊天归档冒充运行结束。
13. 非 coding 与外部动作：用资源/产物版本代替强制 Git，用来源/检查/回执代替强制单测；研究、文档、数据任务同样保护输入与结论边界。发布、发送、预约等动作遵循既有授权。记录可用的操作标识、请求与回执；结果未知先查询对账，未证实可安全重试前不重复。不能用本地日志声称外部 exactly-once。
14. 记录与经验：按项目+任务沿用一个进度入口，按关键变化更新；详细证据通过引用保存。经验附实际事件与适用范围，重复可提高优先级但不自动升级全局规则；独立核验收益/成本和授权后再修规则，不强制 Seen 三次或每个版本必须实跑整 plan 后才修错误。
15. 交付和验证：正式正文保持可读，给按需启动/执行/审查/交接清单与适配要求。候选必须能解释小任务不启用 lane、独立测试、TDD 起点红、单 Claude/单 Codex、隐藏输入、目录迁移冲突、会话中断、外部结果未知、非 coding 产物等场景。文档审查不声称宿主权限/新运行时已经实现。

## 本轮已识别的机制反例
- 按旧修订单剔除 import 后 Java 源码相同、编译均成功，java.util.Date 与 java.sql.Date 运行输出却不同。
- 两个 lane 的 --no-renames 路径集合不相交，目录搬迁仍造成真实 rebase 冲突。
- 独立测试先提交、实现前按预期为红时，实现起点没有相同完整闸的通过凭证。
- HEAD/tree 未变或 Git 显示干净不等同实际输入未变；既有索引标志样例在 inputs 中。
- v2.9 原 §6④ 已有“只限获准差异、同步保护引用、仅停依赖工作、既有授权不重复”，不能被新 approval_source 条款覆盖掉。

## 独立审查要求（来源 coordinator）
审查以上整体方案及其与用户原话/现行要求的关系。给出：总体判断；具体问题的触发条件、影响、证据与最小修改；需要保留的机制；哪些属于可由本次起草解决的方法选择，哪些才缺必要用户决定。请优先解决实际矛盾，避免为了完整而增加必经席位、全局审批、固定次数/阈值或新框架。不要只重审旧修订单。没有必须用户决定时明确写无；若确有问题，原样提出，不擅自替用户决定。
