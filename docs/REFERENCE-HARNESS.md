## Waygoing 实际保存什么

本次归档提交保存 `docs/`、项目入口说明、`.gitmodules` 和四条 submodule 引用。四个第三方仓库的源码文件及完整 Git 历史不进入 Waygoing 的提交；它们仍保存在各自仓库。

`.gitmodules` 记录 URL、路径和跟踪分支，Git 的 submodule 引用另外记录当时检出的 commit。因此“更新时跟随最新默认分支”和“归档时有一个明确版本”可以同时成立。普通 clone 不等于已经取齐子模块源码；需要源码时再初始化。

## 推荐：一个云环境，主仓与参考仓分别配置

建议在现有 Waygoing 云环境的编辑流程中配置：

- 主仓：`BryanYue/Waygoing`，用于自己的文档和以后实现。
- 参考仓：上表四个公开仓库，作为环境中的独立仓库，跟踪默认分支。
- 只准备源码，不安装或启动四套项目的运行依赖。
- 将实际检出路径记录给 agent；本地入口是 `reference-harness/`，云端以环境实际路径为准，不猜固定的 `/workspace` 或 `/opt` 布局。
- 核对没有同时递归初始化 Waygoing 子模块并另克隆同样四份源码，避免重复下载。云端可以直接阅读已配置的独立参考仓。
- 完成准备后 Publish／Republish，再启动一个新任务验证文件可读。只保存草稿不代表已经发布。

当前官方文档说明：环境可以选择多个仓库；发布保存准备好的文件系统，新任务从该状态建立独立工作区；仓库会后台刷新并保留依赖缓存。已有任务保留自己的状态，更新可复用环境要重新发布。官方没有在这页承诺刷新间隔，也没有说明任意手工克隆目录都受后台刷新管理。[OpenAI 官方云环境文档](https://learn.chatgpt.com/docs/environments/cloud-environments)

因此，这个方案可以让每个活动使用已准备的参考资料，无须让 agent 每次主动完整 clone 四遍；它不是所有活动共用一个会实时改变的工作目录。实际账号是否允许把四个公开仓库都加入环境，以及是否存在自动子模块初始化，需在设置时核对。

## 更新到最新怎样设定

建议先使用环境管理的仓库后台刷新，不额外建设常驻更新服务。研究前记录实际 `git rev-parse --short HEAD`；需要严格核对最新时，再针对本次用到的仓库进行 fetch。任务已经引用某个版本后，避免中途更新它造成源码与行号漂移。

如果四仓无法作为环境托管仓库添加，备选是在 Install script 中将它们浅克隆到独立参考目录，并把该目录随环境发布。手工克隆目录的更新要另做：编辑环境时 fetch 并重新发布；不能假设官方后台刷新会覆盖它们。

“每天一次”是可选的新鲜度策略，不是已经创建的计划任务。可以在持久环境中按上次成功更新时间判断，超过 24 小时才增量 fetch；但独立任务内的更新时间不会自动写回环境模板。若要求严格每天统一更新且后续任务共用，需有可持续运行的更新执行器和明确的环境重新发布方式，或采用自己管理的持久主机。当前阶段没有必要先建设这套设施。

## 本地查阅与更新

当前 Mac 的四个目录已经准备好。未来新机器需要恢复归档对应版本时，可以在 Waygoing 根目录执行：

```bash
git submodule update --init --depth 1
```

明确要取最新默认分支时，可以使用：

```bash
git submodule update --init --remote --depth 1
```

这会更新本机子模块检出版本；Waygoing 会显示引用发生变化。是否把新的引用再提交，由当次任务决定。当前归档的引用只记录这次准备结果，不要求以后一直停留在它们上面。

本次只有本地提交，没有推送。以 GitHub 为来源的云环境必须在这些文档和登记信息推送后，才能从远端取得本次归档；发布环境也不能替代 Git 推送。
