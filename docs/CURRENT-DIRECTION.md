## LifeOS 与 Waygoing 的关系

用户已认可：LifeOS 成为 Waygoing 的一个应用方向，通过插件／适配层接入；先借现有 DeepSeek Harness 验证，再随自己的 Waygoing 成长选择适合的能力接入。这里的“子集”指产品中的领域能力，不表示 LifeOS 全部代码都应放进 harness 内核。

- Waygoing 内核负责模型循环、工具执行、上下文、取消和运行记录；LifeOS 保留目标、计划、事实、推断、关系、业务规则及数据。
- 接入层将 LifeOS 能力提供给 agent；现有界面可用于结构化录入和人工决定，是否逐步简化由实际使用反馈决定。
- 会话历史与业务记录分开：agent 的回答不自动成为用户的完成事实。换宿主不应重建另一份个人业务数据或绕开既有规则。
- 第一阶段候选采用薄 DeepSeek 插件调用 LifeOS 本地 API；多个宿主确有共用需要时再考虑 MCP，不先建设通用插件平台。DeepSeek Harness 是开发者预览，有不兼容变更风险；不将其视为已验收的长期稳定底座。

源代码评估基线：LifeOS `d2607cef`、DeepSeek Harness `86a40220`，均已在本次讨论中核对远端默认分支。现有 Agent 入口支持授权读取和新建推断草稿，尚未证明两项目已接通。职责、第一阶段步骤和验证边界见 [Plan C](planning/2026-10-16/PLAN-C.md)。

## 学习方式与技术方向

用户主要使用 **Kotlin，目前不会 Go**；语言学习不阻塞规划。Go 是有理由的倾向，具体模块、工具链和 UI 技术仍可选择。

每个单元保留：必要概念与少量资料 → 用户先提出设计 → Codex 质询 → 用户修订并动手关键机制 → Claude 辅助实现和首轮讲解 → 先预测再运行对照 → Codex 独立 review 与有增量的补充教学。用户不需要手写所有代码，也不能只提出一句需求、让 AI 完全代做设计后听讲。

长期客户端方向是 **共享运行内核，加 CLI、TUI 及以后需要的 UI／客户端**。CLI 与 TUI 可以共存；起步不必拆成多个进程或服务。语言、通信协议、工具数量及完整架构尚未冻结。来源：[Plan B 后续讨论](discussions/2026-10-16-plan-b-and-reference-repositories.md)。

用户已有 DeepSeek／Gemini API，Codex／Claude 订阅用于辅助开发和学习；采购 OpenAI／Anthropic API 不是前置条件。真实调用前仍需明确所用服务、模型及预算。本次资料整理没有调用付费模型 API。

早期教材的固定时间估算、强制核心手写建议，以及“先证明自建价值才继续”的说法，不能覆盖后续澄清。模型训练、微调和从零训练语言模型不在当前学习主线。
