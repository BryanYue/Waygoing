# 个人 Harness 的候选定位

此前讨论倾向于一个较薄的个人任务系统：复用成熟模型与原生 runtime，把用户确有需要的任务状态、写入归属、证据、角色和会话交接做得可靠。这个建议还需要用真实场景验证，不能据此宣布必须自建。

候选职责可以分为三部分：

- 任务管理：保存目标、来源、当前状态、授权、依赖、执行者和产物。任务不依赖某个聊天窗口一直存在。

- 执行后端：可调用原生 Codex／Claude 等 agent，也可直接使用模型 API。不同后端应声明能力差异。

- 验证与交接：检查结果对应哪个版本，是否满足要求，谁还能写入，何时需要继续、换会话或交给用户决定。

确定性的状态转换可以由程序管理；需要理解需求和拆分工作时再调用模型。AI 协调者与运行这些状态转换的软件不是同一个概念。

Go 目前被认为适合进程管理、事件处理、取消、持久状态与接口适配。独立适配进程和结构化协议是候选插件方式，不要求所有插件使用 Go。语言和存储方案尚未冻结。

值得重点评估的成本包括：适配上游版本、重复的权限与上下文管理、模型调度开销、误判导致的阻塞，以及用户维护两套状态的负担。收益看人工接续和纠偏是否减少、重复工作是否下降、验收是否更可靠，不以功能数量衡量。

非 coding 任务也需要目标、来源、动作、产物、回执和授权；Git、worktree、编译测试和 lane 的具体规则应保留为工程场景能力，不直接推广为所有个人事务的必经步骤。

# 长任务与会话释放需要讨论的机制

用户希望长任务可以持续推进，同时允许旧会话结束。现行 W11 已要求按任务保存进度、恢复时核对原始要求和真实状态，也明确不以固定压缩次数或占用率作为默认提质方法。

候选设计中，任务、一次执行和会话分别有自己的身份。新会话接手同一任务，可以读取当前目标、约束、决定原因、产物版本、验证证据、未完成动作和运行中的任务引用。原生压缩可以继续用于单个会话内部；新会话接续解决另一类生命周期问题。

需要重点推敲：

- 哪些可观察问题表明应换会话，例如重复工作、持续遗忘限制、下一步错位，或原生压缩已经无法可靠恢复；不能凭空给一个统一阈值。

- 交接前如何处理正在写入的执行者、后台子任务、等待批准的操作和结果未知的外部动作。

- 如何确认旧执行已经停下、写入归属已经移交。只创建一个新聊天，不等于旧进程与资源已经释放。

- 交接摘要如何引用原始要求和证据；摘要可能出错，不能成为新的唯一授权来源。

- API 直连和原生 CLI 的会话接口不同，如何保留各自的中断、恢复与状态语义。

- 新会话接续后怎样验证没有丢目标、重复执行、沿用失效证据或重新发明已否定方案。

这些是讨论问题，尚无已批准的状态机、触发阈值或会话释放实现。

# 模型 API 与原生 CLI 的接入边界

| 接入方式 | 谁管理执行循环 | 用户系统需要承担什么 |
| - | - | - |
| 直接接模型 API | 自建或集成的 runtime | 上下文、工具执行、错误恢复、权限、预算、停止条件与持久状态 |
| 调用原生 agent CLI／服务 | 原生 Codex、Claude Code 等 runtime | 任务契约、进程／会话生命周期、结构化事件、能力适配、产物核验与外围编排 |

不能只用“输入提示词、返回文字”概括所有后端，否则会丢掉审批、取消、工具失败与会话状态。外围管线与内部 agent 也要明确职责，避免双方重复拆分、重试和控制同一件事。

Codex 本地 [TypeScript SDK 说明](/Users/yueminjun/WorkPlace/codex/sdk/typescript/README.md)描述了通过 CLI 子进程交换 JSONL 的方式；[App Server 文档](https://learn.chatgpt.com/docs/app-server)提供更深入的会话与事件接口。[Claude Code 程序化调用](https://code.claude.com/docs/en/headless)提供非交互执行和结构化输出。原生桌面功能、插件、审批和登录能力能否从选定接口取得，需要按版本确认。

用户关注订阅是否可以用于自己的 harness，以及是否存在账号限制风险。要区分套餐使用额度与 OAuth 登录凭证。2026 年 10 月 15 日查阅官方文档时，讨论得到以下边界：

- Anthropic 区分最终用户登录未修改的 Claude Code，与第三方收集、中转订阅凭证。产品／服务集成还有商业条款及由最终用户自行认证等条件。不能把个人 CLI 用法扩展解释为通用订阅代理。[官方认证与合规说明](https://code.claude.com/docs/en/legal-and-compliance)

- OpenAI 有正式的 Sign in with ChatGPT 订阅授权路径；本地／开源应用与商业、托管应用的接入条件不同。App Server 旧认证也不能直接推广为商业托管认证。[订阅授权开发者说明](https://developers.openai.com/siwc/token-sharing-open-source)、[App Server 认证](https://learn.chatgpt.com/docs/app-server#auth-endpoints)

- 套餐仍有用量限制，不能默认变成无限 API 配额；额度用完后的付费切换应遵守用户选择。[其他应用中的 ChatGPT 套餐使用](https://help.openai.com/en/articles/20001542-using-your-chatgpt-plan-in-other-apps-and-sites)

这些是当时的公开接入依据，不是对具体账号的封禁风险保证，也不是已经完成的集成测试。真正选择接法时需核对当时条款、产品形态和接口能力；不要提取原生凭证或冒充客户端来绕开正式接入。

# Agent Runtime 学习的范围与方法

用户希望通过深入理解运行机制，判断模型在真实任务中的能力边界。学习目标是能够追清失败原因、解释机制的代价，并为自己的工作流做有依据的选择。

| 主线 | 要回答的问题 | 可讨论的练习 |
| - | - | - |
| 一次模型调用 | 模型实际收到哪些材料，哪些信息只存在磁盘或历史里 | 固定任务，改变输入材料，分析结果与证据 |
| Agent 循环 | 谁提出工具请求，谁执行，谁回传结果，谁决定停止 | 亲手写小型调用循环，保留请求与工具往返，制造一次工具失败 |
| 上下文管理 | 历史、摘要、检索、记忆、提示词缓存各有什么职责 | 对比完整历史、按需读取、摘要与新会话接续 |
| Runtime 生命周期 | 中断、取消、恢复、后台任务和权限如何相互作用 | 追踪一次运行被打断后，哪些状态需要核对 |
| 多席位协作 | 分工与上下文隔离带来什么收益和成本 | 比较单执行者与独立测试／审查，检查共享错误前提 |
| Harness 增量 | 新机制是否比维护良好的原生工作流更有效 | 固定验收，每次只增加一个机制，观察返工、成功率与成本 |

模型侧保留对使用有帮助的内容：token、上下文容量、结构化输出、工具使用、推理预算、随机性、事实依据和失效模式。训练、微调、优化器、从零构建模型不列为本次主线。

能力边界要写成“哪个模型或模型加原生 runtime，在何种任务、输入、工具、预算和验收条件下出现什么行为”。不能将上下文缺失、工具失败或权限拒绝统称为模型能力不足，也不能用单次成功证明某种机制普遍有效。

学习方式倾向从熟悉的工程场景开始，少而精地选材料；先预测行为，再跑小实验或读源码，再解释差异。可以由用户亲手完成关键循环，AI 负责解释、检查与提供反例。判断掌握程度看能否复述信息流、定位失败层次并迁移到新场景，不看记住多少框架名称。

# 第一轮语音讨论建议

先围绕一个真实长期任务或一天中的真实事务，说明哪里希望 AI 接手，哪里仍要自己判断。先形成需求和学习问题，再决定框架、插件数或 lane 数。

可以依次讨论，但不要求一次全部完成：

1. 最先服务的两三个真实场景是什么；现有工具已经足够完成哪些部分。

2. 当前最痛的是遗忘与重做、验收不可信、协作冲突，还是跨工具接续；有哪些具体事件。

3. 哪些工作直接处理即可，哪些才需要复杂任务模式。

4. 协调、实施、独立测试、独立审查和最终确认如何分工；谁能改变验收与授权。

5. 会话接续需要保留哪些事实，怎样知道旧执行已停止。

6. 原生 CLI 和直接 API 各承担什么；Go 核心真正需要拥有哪些职责。

7. 用户希望亲手理解和实现哪些机制；用什么小实验检验理解和系统增益。

讨论方式：模型先准确复述用户的具体意思，再提出取舍或反例；每次深入一个主要问题。允许发散和暂缓结论。源码、产品接口和条款问题需要查证时，再做对应的只读核对；不要用语音中的顺畅解释替代证据。

阶段结束时仅记录：已决定的内容及理由、未决问题、需验证假设和下一步。想法不自动升级为需求，方案不自动变成实施授权。讨论积累较多后，可以将 harness 设计与 runtime 学习拆成关联专题，并共同引用同一份已确认方向。
