2. 每个学习专题只设一个主讲模型。另一个模型只在固定检查点做独立复核。[推断]
3. 理由一：瓶颈在你的吸收，不在模型的产出速度。两个模型同讲，阅读量会翻倍。[推断]
4. 理由二：两个模型的解释冲突时，要由你裁决，这会占用学习精力。[推断]

### 协作节奏示例：第一个最小 agent 循环（仅是建议）

1. 预测：主讲给一页材料和 3–5 道预测题。你先写答案，不查资料。[附件:180]
2. 预测题举例：“模型发出工具请求后，谁来执行？”“谁决定停止？”[附件:168]
3. 手写：你用 Go 写最小循环，只接一个模型 API。[附件:41]
4. 范围：只做一个 `read_file` 工具，加一个 `max_turns` 上限。[推断]
5. 记录：每一轮的请求和响应都写入 JSONL。[附件:168]
6. 卡住时：主讲只给提示和文档指向，不直接给完整代码。[推断]
7. 你可以要求直接给答案，但每次要记一笔。[推断]
8. 制造失败：让工具返回错误。先预测，再运行，再对照 JSONL 解释差异。[附件:168]
9. 复述：你用自己的话写出一轮完整的信息流。主讲只指错，不代写。[附件:180]
10. 复核：只给另一个模型看你的代码、JSONL 和复述。[推断]
11. 不给复核模型看主讲的讲解，这样它能独立发现误解。[推断]
12. 对照源码：读 Codex 里对应的实现。回答“它多处理了什么，为什么”。[附件:194]
